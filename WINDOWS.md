The owner approved Full and Compact views and authorized prerelease publication with hardware testing to be performed manually. Build 27 full hardware acceptance is not yet recorded. Use [installation](WINDOWS-INSTALL.md) and [acceptance/limitations](WINDOWS-RELEASE-CANDIDATE.md) for current user guidance. Earlier development-only statements below retain their milestone context.

Windows Preview 0.1.25/build 27 starts in **Hardware control, disconnected**. Choose USB or TCP/IP and click Connect when ready. Simulation remains optional under Connection → Application mode; simulation banners and the simulated-transmit control appear only for simulated sessions. ## Launch modes

In Full view, Disconnect before switching modes. In the existing Connection section, select USB or TCP/IP. For TCP/IP, enter the address and command port; for USB, select a baud rate and choose the COM port after reopening (simulation does not enumerate devices). Under Connection → Application mode, choose the desired mode, click Switch mode, and confirm. Reopening flushes preferences and closes the old service/reader before starting the replacement. Cancel leaves the current session unchanged. Mode changes are rejected while a reader or discovery scan exists or an action is queued.

- **Simulation:** simulated readings, controls and discovery; all hardware connections, startup auto-connect and sharing are blocked by the backend.
- **Read-only:** explicit USB/TCP telemetry connections; every control, power and wake action is rejected by the controller and worker. The transport accepts only an exact allowlist of 26 telemetry/identity query frames, rejecting mixed frames, setters and the USB wake handshake.
- **Hardware control:** explicit USB/TCP connection and existing guarded amplifier controls. The operator supplies/stops RF and sets drive power. Before ATU tuning, verify that the amplifier's existing hardware connections will not unexpectedly request radio transmission.

A mode handoff or endpoint-specific launch refuses to activate an already-open window for the target mode. Close that target window and retry; the existing connection is neither activated nor changed. Ordinary duplicate launches without a new endpoint still activate their existing window. After a reader error or terminal exit, Disconnect remains available while the local service is responsive, so its ownership can be released before changing modes. Abrupt reader termination does not break the state API or replay controls.

Both hardware modes start disconnected, even when saved settings request auto-connect; the operator must click Connect. Discovery also requires an explicit click and performs identification only. There is no automatic mode, tuning, power or wake action during reopen. A persistent mode notice stays visible in Full and Compact, including service failure. Normal production launches start in Hardware control, disconnected; choosing another mode does not silently change the next normal launch. Explicit `--demo` and review-named builds retain offline Simulation startup.

For explicit command-line launches, mutually exclusive `--demo`, `--read-only` and `--hardware` are available. Hardware endpoints require an explicit hardware access mode. Automated `--smoke-test` launches reject both hardware modes. Never use a hardware access flag for an offline test without mocking all physical transports.

## Run

For the review identity, extract the complete review folder and open `KPA1500 Control Review/KPA1500 Control Review.exe`. The production-named candidate uses `KPA1500 Control/KPA1500 Control.exe` and starts in Hardware control, disconnected. Keep `_internal` beside the EXE. Python and native UI libraries are bundled. Windows 11 x64 and Microsoft Edge WebView2 Evergreen Runtime are required. If WebView2 is missing, the app gives installation/repair guidance before starting its backend. No administrator privileges are requested.

Windows settings and view preferences use `%LOCALAPPDATA%/KPA1500 Control/Windows`, separate from earlier Windows Review, OM and Mac settings. Simulation, Read-only and Hardware control have distinct settings, geometry and instance identities derived from the launch base path. On Windows the base path is normalized as an absolute logical path without resolving filesystem storage; saved MSIX settings therefore retain the same instance identity as the corresponding portable launch. Relative paths and dot segments are normalized, and identity comparison is case-insensitive. Explicit test launches use `--demo --settings <new-file> --http-port 0`. No production settings should be supplied to a review session. Full/Compact, Light/Dark, meter, callsign, section visibility and stay-on-top preferences persist independently of the UI's random HTTP origin. Window size/position recover into the current display work area. About reports version/build and review mode. A second normal launch activates the existing window and creates no second reader. Deliberately isolated settings files define separate review identities for automated tests; endpoint leases protect hardware ownership independently.

Coordination applies only to updated copies using the same logical profile identity. Older unpatched MSIX binaries do not participate in the new coordination protocol; close or upgrade them before using another copy. Arbitrary filesystem aliases (such as junctions, symbolic links or hard links) are not merged into one profile identity. Package-private and ordinary settings remain separate storage views; this coordination does not merge their data.

The Windows loopback service uses an ephemeral port by default and the shared telemetry endpoint remains `/api/v1/telemetry`; sharing stays disabled in this offline review. The tokenized UI remains loopback-only with Host/Origin validation. The additional activation endpoint requires the same per-process token, accepts no equipment action, and uses only its validated 127.0.0.1 address.

## Discovery

In Simulation, Disconnect then Auto Discovery demonstrates synthetic progress, cancellation and selecting a simulated amplifier. Selection never connects or saves hardware settings; Connect is separate. No interfaces, COM devices or amplifier addresses are probed by simulated discovery.

The implemented Windows hardware discovery provider (not exercised live) passively enumerates COM ports for explicit user selection, without serial identity probes. Its TCP provider reads the default IPv4 route and directly attached interface, rejects invalid/routed gateway data, limits larger networks to the current /24, preserves smaller subnets, excludes the PC itself and caps TCP targets at 254. It provides bounded identity-only probes, cancellation and manual-IP fallback. This candidate has not been connected to hardware. Any live validation requires separate approval; offline tests use simulation or mocked transports only.

The complete folder also includes an EXE-specific `.exe.config` file beside the EXE. Keep that file with the package: it configures this application's .NET host to load its bundled managed assemblies when the ZIP retains Windows' downloaded-file marker. It does not remove those markers or change Windows, SmartScreen, or machine-wide .NET settings. The packaging audit rejects a missing or modified config.

## Develop and build

Use Python 3.12. `scripts/setup-windows.ps1` creates this project's own `.venv` and installs `requirements-windows.lock.txt`. Setup downloads dependencies; offline tests and simulator execution do not need Internet.

Run `scripts/test-windows.ps1`, then `scripts/build-windows.ps1` for the review identity, or `scripts/build-windows.ps1 -ProductionIdentity` for a separate production-named local candidate. See WINDOWS-RELEASE-IDENTITY.md for metadata and version mapping. The build includes pyserial's Windows implementation and port-listing module, pywebview/pythonnet runtime metadata, the DPI/asInvoker manifest, and dependency notices. The build runs `scripts/check-windows-notices.py`, verifying all notice/source hashes, all frozen module roots and every dependency DLL/PYD/JAR against the reviewed inventory. Changes to dependencies require inventory review.

Dependency notices are version-specific. The owner selected the MIT License for project-owned application code and artwork; see LICENSE and LICENSING.md. Third-party components retain their separate notices. Source builds are unsigned until separately signed. The current signed candidate and exact test scope are recorded in WINDOWS-RELEASE-CANDIDATE.md; signing does not authorize release or Store submission. See WINDOWS-PORT-STATUS.md for historical evidence.

For a Windows release copy, sign the complete native payload rather than only the EXE. Application Control can block unsigned bundled extensions before .NET initializes, even when the EXE signature is valid. `scripts/sign-windows.ps1 -Package <audited-build-folder> -Toc <matching-PYZ-00.toc> -Output <new-separate-folder>` performs an offline provenance/signature audit and prints a plan with source, absolute output and file actions, without copying or signing. Relative output paths follow the active PowerShell filesystem location, including after `Set-Location`; non-filesystem output providers are rejected. Signing requires plain filesystem paths: source roots, source/output ancestors and source descendants must not be junctions, symbolic links or other reparse points. The workflow checks ancestors even above missing output directories and rechecks the paths immediately before copying. Choose a non-redirected directory rather than relying on an alias to reach the package. Adding `-Sign -SignTool <signtool.exe> -Dlib <Azure.CodeSigning.Dlib.dll> -Metadata <local-metadata.json> -ExpectedPublisher <certificate-subject>` contacts the configured Azure signing and timestamp services; it requires separate network authorization when work is otherwise offline. It signs only the reviewed unsigned dependency allowlist and an unsigned application EXE, preserves valid existing signatures byte-for-byte, and rejects other signature failures. Never disable Application Control to make a candidate pass.

The signing workflow verifies pinned dependency/license hashes before signing and all PE signatures afterward, then uses `scripts/check-windows-signing.py --source <pre-sign-folder> --target <signed-folder>` to prove that only appended PE certificate data, its directory entry and the checksum changed. Other payload bytes and file lists must remain identical. The comparison rejects missing, non-directory and empty inputs with a failing exit code. Preserve the matching pre-sign source package and external `.signatures.json` receipt with the evidence. That receipt is a record, not an exemption from dependency provenance or signature verification. The original pinned notice inventory intentionally continues to describe the pre-sign vendor bytes; a post-sign raw-hash audit will differ for the signed dependencies. Third-party license and authorship notices remain unchanged. Test the resulting copy in a fresh offline guest with Application Control enforced, including packaged/portable ownership and clean reopen; signing alone does not establish acceptance.

Closing waits asynchronously for pending preference saves. If saving fails or times out, the window remains open and reports the error. Correct the storage problem and close again to retry the preference save. This mechanism does not retry any amplifier commands.

For isolated Mac cross-platform review, see MAC-REVIEW.md. Its stable review-origin solution applies only to the generated review wrapper; production Mac behavior is unchanged.

For finalized local user documentation, see [installation](WINDOWS-INSTALL.md), [support](WINDOWS-SUPPORT.md) and [data handling](WINDOWS-DATA-HANDLING.md). These newer source documents have not replaced the build-time documents inside the tested signed ZIP.

The guest-only `scripts/test-windows-msix-identity.ps1` checks logical profile identity using a private, non-Store MSIX and portable **review** binaries. Run it only in a fresh Windows Sandbox with networking disabled. Map read-only inputs at `C:\KPAMSIXInput` (private `feasibility-unsigned.msix`, its `package.sha256`, `portable.zip` containing `KPA1500 Control Review`, and the already-staged offline SignTool runtime under `tools`) and writable results at `C:\KPAMSIXResults`. The harness rejects a non-Sandbox user or active network adapter, creates a temporary guest-only signing certificate, and forces every app launch into Simulation. It covers private-only/both-location/ordinary saved settings, both launch orders, fresh profiles, same-format duplicates, logical identity hashes, unchanged saved settings, owner-death recovery with the mode-handoff startup flag, and packaged first-launch/reopen smoke checks. It uninstalls only the fixed private proof package. No Store identity, hardware connection, network download, or production signing is involved; this is separate from final signed-package hardware and multiple-monitor acceptance.

## Packaged network regression

Every Windows build runs `scripts/check-windows-network.py` against the frozen GUI executable after WebView2 loads in an isolated hidden window. It reads local interface configuration without creating an amplifier controller, scanning addresses or opening an equipment connection. A host with no default IPv4 route is recorded as an unsupported discovery layout, rather than a failed helper invocation. The report retains helper failure details for diagnosis. Use `scripts/test-windows.ps1 -FrozenExe '<path-to-exe>'` to include the same check with the standard source regressions, including against a signed package. Numeric discovery progress uses shared Mac/Windows JavaScript and is covered by `tests/test_discovery_ui.cjs`.
